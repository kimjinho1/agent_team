agent-org

AI 직원들이 어떻게 팀을 짜고
진짜로 코드를 만드는가

이 폴더 안의 파일들이 각각 무슨 일을 하는지, 그리고 왜 이런 식으로 만들었는지를 처음 보는 사람 기준으로 설명합니다.

30초 요약

  1. 요구사항 한 줄을 받으면 AI 한 명이 아니라 여러 명이 역할을 나눠 맡습니다.
  2. 각자 다른 지시문(프롬프트)을 받습니다. 그래서 PM처럼, QA처럼 행동합니다.
  3. 서로 기다릴 사람만 기다리고 나머지는 동시에 일합니다.
  4. 중요한 문서는 다른 직원이 검토하고, 퇴짜 맞으면 다시 씁니다.
  5. 결과 코드는 git 새 브랜치에, 문서는 따로 보관됩니다.

1가장 큰 오해부터 풀고 가자

"AI가 코드를 짜준다"고 하면 보통 AI 한 명에게 다 시키는 것을 떠올립니다. "쇼핑몰 만들어줘" 하면 AI가 혼자 끙끙대며 전부 만들어내는 그림이죠.

이 프로그램은 그렇게 안 합니다. 대신 회사를 하나 만듭니다.

비유

학교 조별 과제를 생각해 보세요. 한 명이 조사도 하고, PPT도 만들고, 발표도 하면 결과물이 어정쩡해집니다. 잘하는 조는 역할을 나눕니다. 자료 조사, 디자인, 발표.

그런데 진짜 중요한 건 역할을 나눈 다음입니다. 조사 담당이 뭘 찾았는지 PPT 담당이 알아야 하고, PPT가 나와야 발표 연습을 할 수 있죠. 이 "누가 뭘 기다려야 하나"를 관리하는 게 이 프로그램의 진짜 일입니다.

2AI 한 명을 어떻게 "직원"으로 만드나

비밀은 허무할 정도로 단순합니다. 똑같은 AI에게 서로 다른 지시문을 주는 것뿐입니다.

AI에게 말을 걸 때, 질문 앞에 "너는 지금부터 ○○야" 하고 성격을 정해줄 수 있습니다. 이걸 시스템 프롬프트라고 부릅니다. 게임 캐릭터를 고르는 것과 비슷합니다. 같은 몸인데 직업을 뭘 고르느냐에 따라 쓸 수 있는 기술이 달라지죠. 

QA 직원에게 주는 지시문 (실제 내용):

  "당신은 QA 엔지니어입니다.
   - 근거 없는 지적은 하지 마세요. 코드의 어느 부분인지 짚고,
     재현 경로를 적습니다.
   - 계약서와 구현을 한 줄씩 대조하세요.
   - 사소한 취향 문제로 FAIL을 내지 마세요.
     사용자가 실제로 겪을 문제만 차단 사유입니다."

이렇게 써두면 AI가 실제로 깐깐한 QA처럼 굽니다. "이건 제 취향인데요"라고 트집 잡지 않고, 진짜 문제만 골라냅니다. 16개 직무가 전부 이런 지시문을 하나씩 갖고 있고, 그게 전부 src/roles.mjs 파일 안에 들어 있습니다.

왜 이렇게 만들었나

한 명에게 "PM도 하고 QA도 해"라고 하면, 자기가 만든 걸 자기가 검사하게 됩니다. 사람도 자기 글의 오타는 잘 못 찾잖아요. 역할을 분리하면 남이 만든 걸 보는 눈이 생깁니다. AI도 똑같습니다.

3필요한 사람만 뽑는다

16개 직무가 있다고 매번 16명을 다 부르지는 않습니다. 그러면 돈이 16배로 듭니다 (AI를 부를 때마다 요금이 나갑니다).

그래서 일을 받으면 인사 담당 AI가 먼저 팀을 짭니다. 일감을 읽고 "이건 이 정도 사람이면 되겠다"를 판단합니다. 

"버튼 누르면 숫자 세는 웹 카운터"
  → 3명  PM, FE, QA

"재고관리 시스템 — 입출고 기록, 재고 조회 API,
 관리자 웹 화면, 월간 리포트"
  → 7명  PM, 개발리드, FE, BE 1, BE 2, 데이터, QA
       ↑ 일이 크니까 백엔드를 2명 뽑아서 나눠 맡김
         BE 1 → 입출고 기록 API
         BE 2 → 조회·리포트 API

그런데 AI 인사 담당이 실수할 수도 있습니다. 화면을 만들어야 하는데 프론트엔드 개발자를 안 뽑는다든지. 그래서 빠진 자리는 코드가 강제로 채웁니다.

  • 만들 사람이 아무도 없다 → 프론트엔드 개발자 투입
  • PM과 QA는 무조건 (뭘 만들지 정하는 사람, 됐는지 보는 사람)
  • 구현하는 사람이 둘 이상 → 개발리드 투입 (안 그러면 서로 다르게 만듦)

실패했던 이야기

처음엔 "빠진 자리는 위로 거슬러 올라가며 전부 채우자"고 만들었습니다. 결과는 버튼 하나 만드는 데 사장까지 7명이 출근했습니다. 규칙을 최소한으로 줄이고 나서야 3명으로 줄었습니다.

4누가 누구를 기다리나

여기가 이 프로그램의 심장입니다. 직무마다 "나는 누구 걸 받아야 일을 시작할 수 있다"가 정해져 있습니다. 

PM ──> 기획자 ──┬──> 디자이너 ──┐
                │              ├──> FE ──┬──> QA
                └──> 개발리드 ──┴──> BE ──┘

화살표를 따라가 보세요. 디자이너와 개발리드는 둘 다 기획자만 기다리면 됩니다. 서로를 기다릴 이유가 없죠. 그래서 동시에 일합니다.

개발리드가 API 설계를 끝내면 백엔드 개발자가 바로 시작합니다. 디자이너가 아직 작업 중이어도 상관없습니다. 백엔드는 디자인이 필요 없으니까요.

비유

라면 끓이면서 계란 삶기. 물 끓이는 동안 가만히 서 있지 않고 파를 썰죠. 파 썰기는 물이 끓기를 기다릴 필요가 없으니까요. 하지만 면 넣기는 물이 끓어야 합니다.

이 프로그램은 매 순간 "지금 시작할 수 있는 사람이 누구지?"를 확인하고, 해당하는 사람을 전부 동시에 출발시킵니다.

왜 개발리드가 중요한가

프론트엔드와 백엔드는 원래 서로를 기다려야 합니다. "데이터를 어떤 모양으로 주고받을지"를 모르면 각자 만들 수가 없으니까요.

그래서 개발리드가 먼저 약속을 못 박습니다. "메모 목록은 GET /api/notes 로 부르고, 답은 { data, error } 모양으로 준다." 이 약속만 있으면 둘이 서로 안 물어보고 동시에 만들 수 있습니다.

5혼자 결정하지 못하게 한다

개발리드가 약속을 잘못 정하면 어떻게 될까요? 프론트도 백엔드도 그 잘못된 약속을 따라 만듭니다. 한 명이 틀리면 전부 틀립니다.

그래서 중요한 문서는 다른 직원의 승인을 받아야 넘어갑니다.

누가 썼나누가 검토하나뭘 보나
개발리드PM, 기획자이 문서만 보고 개발자들이 일할 수 있나
아키텍트PM, 개발리드나중에 되돌리기 어려운 결정이 섞였나
디자이너기획자요구한 기능이 화면에 다 있나
기획자PM정한 범위를 벗어났나

검토자가 검토: 보완요청 을 내면 작성자가 다시 씁니다. 실제로 테스트할 때 PM이 개발리드에게 이렇게 퇴짜를 놨습니다: 

1. 3단계 문서가 중간에 끊김 (다음 단계가 막힘)
2. 클라이언트 동작을 "필수" 규칙으로 정함 (범위 초과)
3. 수동 검증 시나리오에 완료 조건 일부가 빠짐

검토가 참견이 되지 않게

검토자마다 자기 직무의 눈만 줍니다. PM에게는 "범위를 벗어났나"만 보게 하고, 코드 스타일은 보지 말라고 못 박습니다. 안 그러면 모두가 모든 것에 트집을 잡아 영원히 안 끝납니다. "취향 문제로 반려 금지"도 프롬프트에 박혀 있습니다.

6이미 있는 프로젝트에 들어갈 때

빈 폴더에서 새로 만드는 건 쉽습니다. 어려운 건 이미 몇 달째 굴러가던 프로젝트에 투입되는 경우입니다. 아무것도 모르고 만들면 기존 규칙을 다 무시한 코드가 나옵니다.

그래서 일을 시작하기 전에 먼저 읽습니다. 두 가지를요.

코드 읽기 — 지금 어떻게 생겼나

파일들을 훑어서 구조·사용 기술·기존 API·코드 규칙을 정리합니다. 이때만 파일 읽기 권한을 주고, 쓰기·삭제·명령 실행은 전부 막습니다. 읽기만 하는 손님이니까요.

git 기록 읽기 — 어쩌다 이렇게 됐나

코드만 봐서는 "왜 이렇게 생겼는지"를 모릅니다. 그건 커밋 기록에 있습니다. 누가 뭘 고쳤고, 어느 파일이 자주 깨졌고, 요즘 어느 방향으로 가고 있는지.

재밌는 점은 이건 AI에게 안 물어봅니다. git 명령어로 직접 뽑으면 정확하고 공짜거든요. AI에게는 그 사실을 건네주고 해석만 시킵니다. 

git 이 알려주는 것 (비용 0원):
  커밋 관례    Conventional Commits 100%, 한국어 100%
  자주 바뀐 파일  src/routes/todos.js (4회)
  최근 방향     feat(search) 커밋 2개

AI 가 해석한 것 ($0.3):
  "할 일 API를 안정화한 뒤 검색 기능으로 넘어가는 중입니다."
  "todos.js는 fix 커밋 3개가 몰린 파일입니다.
   검증·응답형식·동시생성은 한 번씩 버그가 났던 부분이니
   회귀에 주의하세요."

비유

전학 첫날, 교실을 둘러보는 것만으론 부족합니다. "저 자리는 원래 누가 앉았는지", "이 반에서 건드리면 안 되는 주제가 뭔지"를 알아야 실수를 안 하죠. git 기록이 그 역할입니다.

7결과물은 어디로 가나

가장 조심스러운 부분입니다. 남의 프로젝트 폴더에 AI가 파일을 쓰는 거니까요. 원칙은 코드와 문서의 주인이 다르다는 것입니다. 

당신의 프로젝트 폴더
  └─ agent-org/2026-메모삭제 새 브랜치에 코드만 커밋
     · 원래 브랜치는 손도 안 댐
     · 원격 저장소로 push 안 함
     · 우리 문서로 더럽히지 않음

~/.agent-org (도구 전용 폴더)
  └─ projects/내프로젝트/
       knowledge/   ← 지금 상태 (계약, 코드 구조, 남은 일)
       runs/        ← 실행할 때마다의 기록

왜 문서를 남의 저장소에 안 넣나

프로젝트 폴더에 저장소가 여러 개일 수 있습니다. 프론트 저장소, 백엔드 저장소처럼요. 그런데 "API 약속"은 둘 다 봐야 하는 문서입니다. 어느 한쪽에 넣으면 반쪽짜리가 되죠. 그래서 중앙에 모읍니다.

지우기 전에 여러 번 막는다

브랜치를 지우는 건 되돌릴 수 없습니다. 그래서 겹겹이 막아뒀습니다.

상황어떻게 하나
저장 안 한 작업이 있음시작 자체를 거부 (당신 작업을 덮을 수 있음)
사람이 만든 브랜치손도 안 댐
아직 합치지 않은 브랜치남겨둠. --force 를 직접 쳐야 삭제
합치다 충돌남되돌리고 원래 자리로 복귀 (반쯤 합친 상태로 안 둠)

8기억이 쌓인다

두 번째 작업이 첫 번째 작업을 모르면, 매번 처음부터 시작하는 꼴입니다. 그래서 세 가지를 계속 쌓아둡니다.

무엇왜 필요한가
CONTRACTS.md
약속 모음		 첫 작업에서 "답은 {data, error} 모양"이라고 정했으면, 두 번째 작업도 지켜야 합니다. 안 그러면 기존 화면이 깨집니다.
BACKLOG.md
미룬 일		 "휴지통 기능은 이번엔 안 함" 같은 말이 각자 문서에 적히고 사라졌습니다. 이제 한 곳에 모아서 다음 PM이 보고 판단합니다.
CODEBASE.md
HISTORY.md		 코드가 바뀌었을 때만 다시 읽습니다. 안 바뀌었으면 건너뛰어서 돈을 아낍니다.

약속이 쌓일수록 문서는 커집니다. 그걸 통째로 AI에게 보내면 요금이 폭발하겠죠. 그래서 주소 목록 + 가장 최근 약속만 보냅니다. 

실행 20건  →  문서 13.6KB
              AI에게 보내는 건 1.2KB
              (주소 21개는 전부 유지)
