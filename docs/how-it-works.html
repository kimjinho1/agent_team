AI 직원들이 어떻게 팀을 짜고
진짜로 코드를 만드는가

요구사항 한 줄이 들어와서 git 브랜치의 코드가 되어 나가기까지, 어떤 도구가 어떤 순서로 무슨 일을 하는지 이 파일 하나로 설명합니다. 그림과 쉬운 설명이 먼저 나오고, 개발자용 세부는 "코드로 보면"을 눌러 펼치면 됩니다. 처음 보는 말은 용어 사전에 모아 두었습니다.

한눈에 보기

AI 한 명에게 다 시키지 않고, AI로 작은 회사를 만든다. 이게 전부입니다. 나머지는 그 회사가 굴러가게 하는 규칙들입니다.

30초 요약
  1. 요구사항 한 줄을 받으면 인사 담당 AI가 필요한 직원만 뽑습니다(보통 3~9명).
  2. 직원마다 다른 지시문을 받습니다. 그래서 같은 AI가 PM처럼, QA처럼 행동합니다.
  3. 각자 기다릴 사람만 기다리고, 나머지는 동시에 일합니다.
  4. 중요한 문서는 다른 직원이 검토하고, QA가 FAIL을 내면 다시 만듭니다.
  5. 완성된 코드는 그 프로젝트의 git 새 브랜치에, 문서와 기록은 ~/.agent-org에 따로 쌓입니다.

직무 약어 — PM: 무엇을 왜 만들지 정하는 사람 · FE(프론트엔드): 화면을 만드는 개발자 · BE(백엔드): 서버와 데이터를 만드는 개발자 · QA: 다 만든 걸 검사해 통과(PASS)/불합격(FAIL)을 내는 사람. 나머지 직무는 그림 2-3에 모여 있습니다.

그림 1-1 · 요구사항 한 줄이 코드가 되기까지

빨간 점선이 재작업 고리입니다. 몇 번까지 돌지는 옵션으로 정합니다(기본 1번).

비유 · 조별 과제

한 명이 조사도 하고 PPT도 만들고 발표도 하면 결과물이 어정쩡해집니다. 잘하는 조는 역할을 나눕니다.

그런데 진짜 중요한 건 역할을 나눈 다음입니다. 조사 담당이 뭘 찾았는지 PPT 담당이 알아야 하고, PPT가 나와야 발표 연습을 할 수 있죠. 이 "누가 뭘 기다려야 하나"를 관리하는 게 이 프로그램의 진짜 일입니다.

무엇이 AI고, 무엇이 그냥 코드인가

가장 헷갈리는 부분입니다. 판단과 글쓰기는 AI가, 순서·규칙·안전장치는 평범한 코드가 맡습니다. AI는 파일을 직접 쓰지도, git을 만지지도 못합니다.

그림 1-2 · 일의 분담

그래서 AI가 이상한 말을 해도 "남의 파일을 덮어쓰거나 원격에 올리는" 사고는 구조적으로 일어나지 않습니다.

전체 흐름

업무 하나를 처리하는 함수는 runPipeline 하나입니다. 그 안에서 일어나는 일을 순서대로 펼치면 아래 10단계입니다.

그림 2-1 · 실행 한 번의 10단계

오른쪽 회색 글씨는 그 단계가 남기는 파일입니다. 칸 색: 파랑 = AI 한 번 호출, 노랑 = 필요할 때만 AI 호출, 보라 = 여러 AI 병렬 실행, 빨강 = 재작업, 초록 = git, 회색 = 코드만.

3단계 · 필요한 사람만 뽑는다

16개 직무가 있다고 매번 16명을 부르지 않습니다. AI 호출 한 번마다 비용이 나가니까요. 인사 담당 AI가 먼저 일감을 읽고 팀을 제안합니다.

그림 2-2 · 팀 편성 — AI의 제안 위에 코드가 규칙을 덧댄다
"버튼 누르면 숫자 세는 웹 카운터"
  → 3명  PM, FE, QA

"재고관리 시스템 — 입출고 기록, 재고 조회 API, 관리자 웹 화면, 월간 리포트"
  → 7명  PM, 개발리드, FE, BE 1, BE 2, 데이터, QA
       ↑ 일이 크니까 백엔드를 2명 뽑아서 나눠 맡김
         BE 1 → 입출고 기록 API      BE 2 → 조회·리포트 API
실패했던 이야기

처음엔 "빠진 자리는 위로 거슬러 올라가며 전부 채우자"고 만들었습니다. 결과는 버튼 하나 만드는 데 사장까지 7명이 출근했습니다. 규칙을 최소한으로 줄이고 나서야 3명으로 줄었습니다.

5단계 · 누가 누구를 기다리나

여기가 심장입니다. 직무마다 "나는 누구 걸 받아야 시작할 수 있다"가 정해져 있습니다. 16개 직무 전체의 관계는 이렇습니다.

그림 2-3 · 16개 직무의 선후 관계 (roles.mjs 의 deps)

디자이너와 개발리드는 둘 다 기획자만 기다리면 됩니다. 서로를 기다릴 이유가 없으니 동시에 일합니다.

뽑히지 않은 직무는 건너뛰고, 그 직무가 기다리던 사람을 대신 기다립니다. 기획자를 안 뽑았다면 개발리드는 PM을 기다립니다. 기획자가 없다고 PM보다 먼저 시작하면 안 되니까요.

앞의 실패 이야기와 헷갈리기 쉬운데, 둘은 다른 이야기입니다. 거기서 버린 건 빠진 직무를 사람으로 더 뽑는 것이고, 여기서 하는 건 이미 뽑힌 사람끼리 누구를 기다릴지 정하는 것입니다. 기획자를 새로 뽑지 않고, 기다리는 대상만 바꿉니다.

그림 2-4 · 시간축으로 본 한 번의 실행 (7명 팀 예시)

회색은 선행을 기다리는 시간입니다(시간은 예시). 막대가 겹치는 구간만큼 혼자 할 때보다 빨라집니다. 실제 수치는 PM 진행 점검 문서에 표로 남습니다.

비유 · 라면 끓이기

물 끓이는 동안 가만히 서 있지 않고 파를 썹니다. 파 썰기는 물이 끓기를 기다릴 필요가 없으니까요. 하지만 면 넣기는 물이 끓어야 합니다. 이 프로그램은 매 순간 "지금 시작할 수 있는 사람이 누구지?"를 확인하고, 해당하는 사람을 전부 동시에 출발시킵니다.

왜 개발리드가 중요한가

프론트엔드와 백엔드는 원래 서로를 기다려야 합니다. "데이터를 어떤 모양으로 주고받을지"를 모르면 각자 만들 수가 없으니까요. 그래서 개발리드가 먼저 약속을 못 박습니다. "메모 목록은 GET /api/notes로 부르고, 답은 { data, error } 모양으로 준다." 이 약속만 있으면 둘이 서로 안 물어보고 동시에 만들 수 있습니다.

코드로 보면 실행 루프의 뼈대 
// src/pipeline.mjs — runExecutionLoop (요약)
const ready = () => roster.filter((p) =>
  !done.has(id(p)) && !failed.has(id(p)) && !running.has(id(p)) &&
  personDeps(p, roster).every((d) => done.has(id(d))));   // 선행이 다 끝났나

while (done.size + failed.size < roster.length) {
  if (signal.cancelled) break;
  if (!budgetLeft()) { overBudget = true; break; }        // 예산 초과면 새로 출발 안 함

  for (const p of ready())                                   // 준비된 사람 전원 동시 출발
    running.set(id(p), runPerson(p).then(reviewGate).then(markDone));

  if (running.size === 0) break;
  await Promise.race(running.values());                      // 누구든 하나 끝나면 다시 확인
}
  • 병렬의 정체: Promise.race로 "누군가 끝날 때까지" 기다렸다가 곧바로 ready()를 다시 계산합니다. 정해진 차수(웨이브)가 있는 게 아니라 끝나는 순간마다 다음 사람이 풀립니다.
  • 스택 확정: decidesStack 직무(아키텍트·개발리드)가 끝나면 그 산출물의 JSON을 읽어 팀 전체 스택으로 저장합니다. 정할 사람이 없거나 실패하면 DEFAULT_STACK(바닐라 HTML + Express)으로 채웁니다.
  • 중단: 대시보드의 "중단"은 signal.cancelled = true로 표시만 합니다. 지금 돌고 있는 단계는 끝까지 가고, 다음 단계부터 멈춥니다.
  • 최종 상태: 취소 → cancelled, 예산 초과 → over_budget, 실패한 사람이 있으면 → failed, 아니면 done. 코드 커밋은 done일 때만 합니다.

직원 한 명은 어떻게 일하나

비밀은 허무할 정도로 단순합니다. 똑같은 AI에게 서로 다른 지시문을 주는 것뿐입니다. 그 지시문을 어떻게 조립하느냐가 결과를 가릅니다.

AI에게 말을 걸 때 질문 앞에 "너는 지금부터 ○○야" 하고 성격을 정해 줄 수 있습니다. 이걸 시스템 프롬프트라고 부릅니다. 게임 캐릭터를 고르는 것과 비슷합니다. 같은 몸인데 직업을 뭘 고르느냐에 따라 쓸 수 있는 기술이 달라지죠.

QA 직원에게 주는 지시문 (실제 내용 일부):

  "당신은 QA 엔지니어입니다.
   - 근거 없는 지적은 하지 마세요. 코드의 어느 부분인지 짚고, 재현 경로를 적습니다.
   - 계약서와 구현을 한 줄씩 대조하세요. 경로·필드명·타입·에러코드까지.
   - 사소한 취향 문제로 FAIL을 내지 마세요. 사용자가 실제로 겪을 문제만 차단 사유입니다."

지시문은 여러 겹으로 조립된다

직원마다 필요한 것만 받습니다. 모든 걸 다 주면 비용이 늘고, 오히려 범위가 흔들립니다.

그림 3-1 · 한 단계에 보내는 지시문의 구성
왜 나눠 주나

구현자에게 "남은 일" 목록을 주면 "이것도 해야 하나?" 하고 범위가 흔들립니다. 범위를 정하는 PM과 기획자만 보면 됩니다. 코드베이스 설명은 첫 단계에서 한 번 읽으면 충분한데, 매 단계 다시 보내면 같은 내용에 계속 돈을 냅니다.

한 번에 다 쓰지 않고 단계로 나눈다

직원은 2~3단계로 나눠 일합니다. 산출물 종류에 따라 쌓는 방식이 다릅니다.

그림 3-2 · 문서는 쌓고, 코드는 다시 쓴다

AI 직원은 손이 없다

직원 AI는 파일을 읽거나 쓰거나 명령을 실행할 수 없습니다. 오직 글을 받아 글을 돌려줄 뿐입니다. 받은 글을 파일로 저장하고 git에 커밋하는 건 우리 코드가 합니다.

그림 3-3 · 권한의 세 단계
코드로 보면 runPerson · runStep 
// src/pipeline.mjs — runStep (요약)
for await (const message of query({
  prompt,
  options: {
    systemPrompt: role.systemPrompt,
    maxTurns: 6,
    disallowedTools: NO_TOOLS,       // allowedTools 는 "자동 승인" 목록일 뿐 — 막으려면 여기
    includePartialMessages: true,   // 글자 조각을 스트림으로 받는다
  },
})) {
  if (message.type === 'stream_event') { text += delta; /* 1초마다 DB 저장 */ }
  else if (message.type === 'result')  { cost = message.total_cost_usd; usage = message.usage; }
}
  • 상한값: 선행 산출물 한 명당 DEP_CAP = 14000자, 이어 쓸 문서는 CARRY_CAP = 9000자를 넘으면 앞부분을 제목 목록으로 접습니다. 코드는 자르지 않습니다.
  • 코드 추출: revise 직무는 답에서 첫 번째 ``` 코드블록만 꺼내 파일로 씁니다. 코드블록이 없으면 이전 버전을 유지합니다.
  • 회귀 점검: QA의 regressionStep은 일감 성격이 new가 아닐 때만 마지막 "최종 판정" 바로 앞에 끼워 넣습니다.
  • 기록: 단계 시작 때 stages.status='running', 단계 번호·이름, 끝나면 done과 비용·토큰 4종·산출물 경로를 저장합니다. 화면은 이 행을 읽어 그립니다.

혼자 결정하지 못하게 한다

개발리드가 약속을 잘못 정하면 프론트도 백엔드도 그 잘못된 약속을 따라 만듭니다. 한 명이 틀리면 전부 틀립니다. 그래서 두 겹의 확인 장치를 둡니다. 만든 직후의 검토, 다 만든 뒤의 QA 재작업.

검토 게이트 — 만든 직후

그림 4-1 · 검토 게이트
누가 썼나누가 검토하나검토 관점 (REVIEW_LENS)
기획자PM요구사항과 완료 조건을 벗어나거나 빠뜨린 것이 없는가, 이번 범위를 넘지 않는가
디자이너기획자유저 스토리와 수용 기준이 빠짐없이 반영됐는가, 예외 흐름이 누락되지 않았는가
개발리드PM, 기획자(PM 관점) + (기획자 관점)
아키텍트PM, 개발리드(PM 관점) + 구현자들이 이 문서만으로 서로 묻지 않고 일할 수 있는가

실제로 테스트할 때 PM이 개발리드에게 이렇게 퇴짜를 놨습니다.

1. 3단계 문서가 중간에 끊김 (다음 단계가 막힘)
2. 클라이언트 동작을 "필수" 규칙으로 정함 (범위 초과)
3. 수동 검증 시나리오에 완료 조건 일부가 빠짐
검토가 참견이 되지 않게

검토자마다 자기 직무의 눈만 줍니다. PM에게는 "범위를 벗어났나"만 보게 하고 코드 스타일은 보지 말라고 못 박습니다. 안 그러면 모두가 모든 것에 트집을 잡아 영원히 안 끝납니다. "취향 문제로 반려하지 마세요"도 검토 지시문에 박혀 있습니다.

QA 재작업 — 다 만든 뒤

그림 4-2 · 재작업 고리

기술 스택은 설계 담당 직원이 정한다

React로 만들지 바닐라로 만들지는 카탈로그가 미리 정하지 않습니다. 아키텍트(없으면 개발리드)가 산출물 끝에 JSON을 쓰면 프로그램이 그걸 읽어 구현자들의 파일 이름을 정합니다.

그림 4-3 · 스택 결정이 파일 이름이 되기까지

경로 검사는 AI가 ../../.ssh/config 같은 이상한 경로를 적어도 repo 밖에 파일이 생기지 않게 하는 첫 번째 방어선입니다. 두 번째는 커밋 직전의 writeIntoRepo입니다.

PM의 진행 점검 — 끝난 뒤

모든 구현이 끝나면 PM이 한 번 더 일합니다. 이번엔 추측이 아니라 실측 표를 받습니다. 직원별 시작·종료 시각, 직접 일한 시간(소요)과 선행을 기다린 시간(대기), 비용, 재작업 횟수. 대기가 길면 순서 문제이고 소요가 길면 일 자체가 무거운 겁니다. 둘은 해법이 다릅니다.

코드로 보면 판정 규칙과 대기 시간 계산
  • 검토 통과 여부는 마지막 줄만 보지 않고 답 전체에서 /검토:\s*보완요청/이 보이는지로 판단합니다. 없으면 승인입니다.
  • QA 판정은 /판정:\s*FAIL/로 봅니다. QA 지시문이 "마지막 줄에 반드시 판정: PASS 또는 판정: FAIL"을 요구합니다.
  • 대기 시간 = 이 사람의 시작 시각 − 선행자들 중 가장 늦게 끝난 시각. buildTimingReport가 표로 만들어 runStandup에 넘깁니다.
  • --no-review로 검토 게이트를 끌 수 있습니다. 빠르고 싸지만 한 명의 실수가 그대로 퍼집니다.

기억과 git

가장 조심스러운 부분입니다. 남의 프로젝트 폴더에 AI가 만든 파일을 넣는 거니까요. 원칙은 하나, 코드와 문서의 주인이 다르다.

그림 5-1 · 결과물은 두 곳으로 갈라진다
왜 문서를 남의 저장소에 안 넣나

프로젝트 폴더에 저장소가 여러 개일 수 있습니다. 프론트 저장소, 백엔드 저장소처럼요. 그런데 "API 약속"은 둘 다 봐야 하는 문서입니다. 어느 한쪽에 넣으면 반쪽짜리가 되죠. 그래서 중앙에 모읍니다.

기억이 쌓인다 — 다음 작업이 이어받는 것

두 번째 작업이 첫 번째 작업을 모르면 매번 처음부터 시작하는 꼴입니다. 그래서 네 가지를 계속 쌓고, 필요한 직원에게만 나눠 줍니다.

그림 5-2 · 실행 사이를 잇는 기억

점선은 "필요할 때만" 갱신된다는 뜻입니다. 코드가 그대로면 코드 파악을 건너뛰어 돈을 아낍니다.

약속이 쌓일수록 문서는 커집니다. 그걸 통째로 AI에게 보내면 요금이 폭발하겠죠. 그래서 주소 목록 + 가장 최근 약속 1건(5,000자까지)만 보냅니다.

실행 20건  →  CONTRACTS.md 13.6KB
              AI에게 보내는 건 1.2KB   (엔드포인트 주소 21개는 전부 유지)

이미 있는 프로젝트에 들어갈 때

빈 폴더에서 새로 만드는 건 쉽습니다. 어려운 건 이미 몇 달째 굴러가던 프로젝트에 투입되는 경우입니다. 그래서 일을 시작하기 전에 먼저 읽습니다.

비유 · 전학 첫날

교실을 둘러보는 것만으론 부족합니다. "저 자리는 원래 누가 앉았는지", "이 반에서 건드리면 안 되는 주제가 뭔지"를 알아야 실수를 안 하죠. git 기록이 그 역할입니다.

화면은 어떻게 살아 움직이나

대시보드는 서버에서 받은 상태를 그리는 것뿐입니다. 서버는 0.5초마다 상태를 확인해 바뀌었을 때만 밀어주고, 화면은 그걸 받아 보드와 픽셀 사무실을 다시 그립니다.

그림 6-1 · 업무 지시부터 화면 갱신까지
왜 확인 창을 한 번 거치나

업무를 던지자마자 돌리면 "이렇게 많이 뽑을 줄 몰랐다", "커밋 안 한 파일이 있었다"를 돈을 쓴 뒤에 알게 됩니다. 브리핑은 인사 담당 호출 한 번이라 싸고, 여기서 짠 팀은 그대로 재사용되므로 같은 값을 두 번 내지 않습니다.

왜 픽셀 사무실인가

그림 6-2 · 상태가 그림이 되는 규칙

그냥 예쁘라고 만든 게 아닙니다. 진행 상황은 한눈에 안 들어오면 의미가 없습니다. 표로 "FE: running, BE: running"이라고 쓰면 읽어야 알지만, 두 명이 책상에 앉아 타이핑하고 있으면 그냥 보입니다. 넷이 누워 있으면 "아직 대기구나"가 바로 와닿고요.

코드로 보면 화면 쪽 구조
  • public/dashboard.html이 new EventSource('/events')로 상태를 받아 latestState에 담습니다. 타이머 세 개가 돕니다: 사무실 그리기 70ms, 보드 다시 그리기, 지난 실행 목록 5초.
  • public/pixel.js에는 앱 상태를 모르는 순수 그림 함수 31개가 있습니다. 모두 첫 인자로 "점 찍기" 함수 p(x, y, w, h, color)를 받습니다. 모듈이 아니라 일반 <script>라서 dashboard.html의 스크립트와 전역 범위를 공유하고, 그래서 태그 순서가 중요합니다.
  • 서버의 getState()는 가장 최근 작업의 직원별 상태, 쓰는 중인 글, 비용·토큰, 직무별 누적값을 한 JSON으로 묶습니다. 문자열이 이전과 같으면 보내지 않습니다.
  • 서버가 켜질 때 running으로 남은 행은 failed로 정리합니다. 이전 프로세스가 도중에 죽었으면 영원히 "일하는 중"으로 보이기 때문입니다.
  • 포트가 막혀 있으면 다음 번호로 최대 12번까지 옮겨 갑니다(--port로 고정했으면 옮기지 않음).

그림 7-2 · query() 한 번의 왕복
왜 외부 라이브러리가 두 개뿐인가

빌드 단계가 없으니 npm install 하고 바로 실행됩니다. 화면도 React 같은 틀 없이 HTML 파일을 그대로 읽습니다. 고칠 때 "이 라이브러리가 뭘 하는지"를 따로 공부할 필요가 없습니다.

코드로 보면 인증과 비용

bin/agent-org.mjs가 시작할 때 실행한 폴더의 .env를 먼저, 그다음 설치 폴더의 .env를 읽습니다. process.loadEnvFile은 이미 있는 환경변수를 덮어쓰지 않으므로 먼저 읽은 쪽이 이깁니다. 파일이 없으면 ENOENT를 던지기 때문에 try로 감쌉니다.

// bin/agent-org.mjs
const loadEnv = (dir) => {
  try { process.loadEnvFile(path.join(dir, '.env')); } catch { /* 없으면 넘김 */ }
};
loadEnv(cwd);      // 프로젝트별 설정이 우선
loadEnv(pkgRoot);  // 없으면 설치 폴더

SDK는 CLAUDE_CODE_OAUTH_TOKEN으로 로그인합니다. 화면의 달러 금액은 SDK가 계산한 total_cost_usd를 합친 값이고, 작업 1건당 예산(--budget, 기본 $10)을 넘으면 다음 직원을 출발시키지 않습니다.

왜 roles.mjs 하나에 다 몰았나

직무 하나를 추가하거나 지시문을 바꾸면 팀 편성 후보, 실행 순서, 검토 관계, 회사 규칙 문서, 직무 정의서, 대시보드의 직원 명부가 전부 자동으로 바뀝니다. 같은 정보를 여러 곳에 적어 두면 언젠가 서로 어긋납니다.

코드로 보면 직무 하나의 모양 
// src/roles.mjs — CATALOG 의 한 항목 (요약)
{
  key: 'lead', label: '개발리드', category: '개발',
  deps: ['planner'],               // 기획자가 끝나야 시작
  reviewedBy: ['pm', 'planner'],     // 이 둘의 승인을 받아야 확정
  decidesStack: true,              // 기술 스택을 정할 수 있다
  defaultArtifact: 'interface.md', mode: 'append',
  systemPrompt: '당신은 개발 리드입니다. …',
  steps: [ { label: '스택 확인·데이터 모델', prompt: … },
           { label: 'API 명세', prompt: … },
           { label: '에러·경계', prompt: … } ],
}

구현 직무(FE·BE·모바일·데이터·ML)는 stackKey로 어느 영역 파일을 쓰는지, splittable로 여러 명 뽑을 수 있는지를 표시합니다. PM은 watchdog(마지막에 진행 점검), QA는 regressionStep(기존 코드를 건드린 작업이면 회귀 점검 추가)을 갖습니다.

용어 사전

문서에 나오는 말 중 처음 보면 낯선 것들.

에이전트스스로 단계를 나눠 일하는 AI. 여기서는 "직무를 맡은 AI 직원 한 명"을 뜻한다.
시스템 프롬프트AI에게 먼저 주는 성격 설정. "당신은 QA 엔지니어입니다…" 같은 글.
프롬프트AI에게 보내는 요청 글. 여기서는 요구사항·선행 산출물·이번 단계 지시를 이어 붙인 한 덩어리.
산출물직원이 내놓는 결과 파일. 문서(requirements.md)이거나 코드(index.html).
선행 (deps)"이 사람이 끝나야 내가 시작할 수 있다"의 그 사람. 직무마다 roles.mjs에 적혀 있다.
병렬여러 명이 동시에 일하는 것. 서로 기다릴 이유가 없는 사람끼리만 가능하다.
계약 (인터페이스)프론트와 백엔드가 주고받을 데이터의 약속. 경로·필드명·응답 모양·에러 코드.
기술 스택무엇으로 만들지의 선택. 예: 프론트는 React, 백엔드는 Express, DB는 SQLite.
검토 게이트중요한 산출물이 다음 사람에게 넘어가기 전에 관련자 승인을 받는 관문.
재작업QA가 FAIL을 내면 구현자들이 지적을 반영해 다시 만드는 것.
회귀새 기능을 넣다가 원래 되던 게 깨지는 것. 기존 코드를 건드린 작업이면 QA가 따로 본다.
온보딩기존 프로젝트에 처음 들어갈 때 코드와 git 기록을 읽어 파악하는 단계.
백로그"이번엔 안 하기로 한 것" 목록. 다음 작업의 PM이 보고 고른다.
브랜치git에서 원래 코드를 건드리지 않고 따로 작업하는 갈래. 합칠지 버릴지 나중에 정한다.
커밋 · push · merge커밋은 변경을 저장, push는 원격에 올리기, merge는 갈래를 합치기. 이 도구는 커밋까지만 한다.
SDK어떤 서비스를 코드에서 쉽게 쓰게 해 주는 도구 묶음. 여기서는 Claude를 부르는 도구.
토큰AI가 글을 세는 단위. 대략 글자 조각. 많이 보내고 많이 받을수록 비용이 든다.
SQLite서버 없이 파일 하나로 도는 데이터베이스.
SSEServer-Sent Events. 서버가 브라우저로 계속 소식을 밀어주는 연결.
큐줄 서기. 업무가 여러 개 들어오면 하나씩 차례로 처리한다.
PM · FE · BE · QAPM은 무엇을 왜 만들지 정하는 사람, FE(프론트엔드)는 화면, BE(백엔드)는 서버와 데이터, QA는 품질 검사. ML은 머신러닝, DevOps는 배포·운영.
JSON프로그램끼리 데이터를 주고받는 글 형식. {"이름": "값"} 모양. AI가 팀 명단이나 스택을 이 형식으로 적으면 코드가 읽는다.
API · 엔드포인트API는 프로그램이 다른 프로그램에 일을 시키는 창구. 엔드포인트는 그 창구 하나의 주소. 예: GET /api/notes.
HTTP · GET · POST브라우저와 서버가 대화하는 규칙. GET은 "달라", POST는 "받아라(처리해라)". 202는 "받았고 나중에 처리할게"라는 응답 번호.
환경변수 · .env코드 밖에 두는 설정값. 비밀번호 같은 로그인 토큰을 코드에 적지 않으려고 .env 파일에 둔다.
Promise · 비동기"나중에 끝날 일"을 기다리지 않고 다음 일을 하는 방식. Promise는 그 "나중에 올 결과"를 담는 상자. Promise.race는 여러 상자 중 하나라도 열리면 깨워 준다.
HEADgit에서 지금 보고 있는 커밋. HEAD가 바뀌었다 = 지난번 이후 새 커밋이 생겼다.
Conventional Commitsfeat: …, fix: …처럼 커밋 메시지 앞에 종류를 붙이는 관례.
WALSQLite 저장 방식 중 하나. 쓰는 중에도 다른 쪽이 읽을 수 있어서, 서버가 기록하는 동안 화면이 읽어 가도 막히지 않는다.
직무를 추가하거나 지시문을 바꾸려면 src/roles.mjs만 고치면 됩니다. 설치와 명령어는 README.md에 있습니다.
